## Správa procesů

**Správa procesů** (*process management*) zahrnuje:

- **přepínání kontextu** (*dispatcher*) – fyzické odebírání a přidělování procesoru na základě rozhodnutí plánovače,
- **plánovač** (*scheduler*) – rozhoduje, který proces poběží a případně jak dlouho,
- **správu paměti** (*memory management*) – přiděluje paměť,
- podporu **meziprocesové komunikace** (*inter-process communication*, *IPC*) – signály, RPC,…

### Proces

**Proces** je *běžící program*. V operačním systému je definován:

- identifikátorem (*PID*),
- stavem jeho *plánování*,
- *programem*, kterým je řízen,
- obsahem *registrů* (včetně EIP a ESP apod.),
- *zásobníkem* – rozpracované funkce,
- *daty* – statická inicializovaná a neinicializovaná data, hromada, individuálně alokované úseky paměti,
- využitím *dalších zdrojů OS* a vazbami na *další objekty OS* – otevřené soubory, signály, PPID, UID, GID, semafory, sdílená paměť, sdílené knihovny,…

V OS bývá proces *reprezentován* strukturou označovanou jako **process control block** (*PCB*) nebo též *task control block* či *task struct* apod.

## Plánování procesů

**Plánovač** rozhoduje, *který proces* (procesy) poběží a případně *jak dlouho*.

Při **nepreemptivním plánování** může ke změně běžícího procesu dojít pouze tehdy, pokud to běžící proces umožní *předáním řízení jádru* tím, že *požádá o službu* – typicky I/O operace, volání `exit` (konec), volání `yield` (vzdání se CPU).

Při **preemptivním plánování** může navíc ke změně běžícího procesu dojít, aniž by tento jakkoliv přepnutí kontextu napomohl, a to na základě *přerušení* – typicky od časovače, ale může se jednat i o jiné přerušení.

Vlastní *přepnutí kontextu* řeší na základě rozhodnutí plánovače tzv. **dispečer**.

### Přepnutí kontextu

Dispečer **odebere procesor procesu A** a **přidělí ho procesu B**, což typicky zahrnuje:

- **úschovu stavu** (některých) **registrů** (včetně různých řídicích registrů) v rámci procesu A *do PCB*,
- úpravu některých *řídicích struktur v jádře*,
- **obnovu stavu** (některých) **registrů** v rámci procesu B *z PCB*,
- **předání řízení na adresu**, kde bylo dříve *přerušeno provádění* procesu B.

**Neukládá se/neobnovuje se** *celý stav procesů* – např. se uloží jen ukazatel na tabulku stránek, tabulka stránek a vlastní obsah paměti procesu může zůstat.

*Přepnutí trvá* přesto typicky **stovky až tisíce instrukcí** – interval mezi přepínáním musí být tedy volen tak, aby režie přepnutí nepřevážila běžný běh procesů.

### Plánovací algoritmy

Klasické **plánovací algoritmy** uvedené níže se používají přímo, případně v různých modifikacích a/nebo kombinacích.

#### First come, first serve (FCFS)

Procesy čekají na přidělení procesoru ve **FIFO frontě**. Při *vzniku* procesu, jeho *uvolnění z čekání*, nebo *vzdá-li se* proces procesoru, je tento **proces zařazen na konec fronty**. Procesor se přiděluje procesu na začátku fronty.

Algoritmus je **nepreemptivní** a k přepnutí kontextu dojde pouze tehdy, pokud se běžící proces vzdá procesoru.

#### Round-robin (RR)

Pracuje *podobně jako FCFS*, navíc má ale každý proces přiděleno **časové kvantum**, po jehož vypršení je mu odebrán procesor a proces je zařazen na konec fronty připravených procesů. Je to tedy **preemptivní** obdoba FCFS.

#### Shortest job first (SJF)

Také známý jako **shortest job next** (*SJN*). Přiděluje procesor procesu, který požaduje **nejkratší dobu** pro své další provádění na procesoru bez I/O operací. Je to **nepreemptivní** algoritmus, který nepřerušuje proces před dokončením jeho aktuální výpočetní fáze. Minimalizuje se tak *průměrná doba čekání* a zvyšuje **propustnost systému**.

Je ale nutné **znát dopředu dobu běhu procesů** na procesoru nebo mít možnost ji *rozumně odhadnout* na základě předchozího chování. Používá se pro **opakovaně prováděné podobné úlohy**, zejména ve *specializovaných systémech*.

**Hrozí stárnutí** (*hladovění*, *starvation*) – procesy s dlouhou výpočetní fází čekají na procesor a mohou být neustále předbíhány kratšími výpočty.

**Shortest remaining time** (*SRT*) je obdoba SJF s **preempcí** při vzniku či uvolnění procesu.

### Víceúrovňové plánování

Při **víceúrovňovém plánování** jsou procesy rozděleny **do různých skupin** – typicky *podle priority*, ale lze i jinak, např. dle typu procesu. *V rámci každé skupiny* může být použit **jiný dílčí plánovací algoritmus**. Je použit také algoritmus, který určuje, *ze které skupiny bude vybrán proces*, který má aktuálně běžet (často jednoduše na základě priority skupin). **Může hrozit hladovění** některých (obvykle méně prioritních) procesů.

Linux používá **víceúrovňové prioritní plánování** se *100 základními statickými prioritními úrovněmi*, doplněné o rozlišování *několika typů procesů*:

- Priority 1–99 pro procesy **reálného času** plánované [[#First come, first serve (FCFS)|FCFS]] nebo [[#Round-robin (RR)|RR]].
- Priorita 0 pro **běžné procesy** plánované [[#Completely fair scheduler (CFS)|CFS]].
- V rámci úrovně 0:
	- jsou používány *podúrovně* v rozmezí -20 (nejvyšší) až 19 (nejnižší), nastavené uživatelem příkazy `nice` či `renice`;
	- rozlišuje se plánování pro *běžné*, *dávkové* (delší kvantum, jistá penalizace) a „*idle*“ (zvláště nízká priority) procesy.

### Completely fair scheduler (CFS)

Plánovač dříve používaný *v Linuxu*^[Od verze 6.6 nahrazen EEVDF.]. Snaží se explicitně každému procesu poskytnout **odpovídající procento strojového času** dle jejich priorit. Vede si u každého procesu údaj o tom, **kolik procesorového času strávil**. Navíc má údaj o *minimálním stráveném procesorovém čase*, který dává nově připraveným procesům.

Procesy se udržují ve **vyhledávací stromové struktuře** (red-black strom) *podle využitého procesorového času*. Vybírá se jednoduše proces s **nejmenším stráveným časem**. Procesy nechává CFS běžet po nějaké **časové kvantum** s *rychlostí virtuální času ovlivněnou prioritou* (nižší prioritě běží virtuální čas rychleji) a pak je zařadí *zpět do plánovacího stromu*.

## Synchronizace procesů

**Současný přístup** několika paralelních procesů (vláken, obslužných rutin přerušení či signálů,…) ke **sdíleným zdrojům** (sdílená data, sdílená I/O zařízení) může vést k **nekonzistencím** zpracovávaných dat kvůli *nesprávnému pořadí provádění* různých dílčích operací *různými procesy*.

**Časově závislá chyba** (*race condition*, *souběh*) je chyba vznikající při přístupu ke sdíleným zdrojům kvůli **různému pořadí provádění** jednotlivých paralelních výpočtů v systému, tj. kvůli jejich *různé relativní rychlosti*.

*Zajištění konzistence dat* vyžaduje mechanismy **synchronizace procesů** zajišťující **správné pořadí** provádění spolupracujících procesů.

### Kritické sekce

Máme $n$ procesů soutěžících o přístup ke sdíleným zdrojům. Každý proces je řízen určitým programem.

**Sdílenými kritickými sekcemi** daných procesů rozumíme ty úseky jejich řídicích programů *přistupující ke sdíleným zdrojům*, jejichž provádění jedním procesem *vylučuje současné provádění* libovolného z těchto úseků ostatními procesy.

**Problémem kritické sekce** rozumíme problém zajištění korektní synchronizace procesů na množině sdílených kritických sekcí, což zahrnuje:

1. **vzájemné vyloučení** (*mutual exclusion*) – nanejvýš jeden (obecně $k$) proces(ů) je v daném okamžiku v dané množině sdílených KS,
2. **dostupnost KS** – je-li KS volná, proces nemůže neomezeně čekat na přístup do ní. Je zapotřebí se vyhnout *uváznutí*, *blokování* a *stárnutí*.

### Problémy vznikající na kritické sekci

**Data race** (*časově závislá chyba nad daty*, *souběh nad daty*) jsou dva přístupy ke zdroji s výlučným přístupem ze dvou procesů bez synchronizace, kdy alespoň jeden přístup je pro zápis.

**Uváznutí** (*deadlock*) při přístupu ke zdrojům s výlučným (omezeným přístupem) je situace, kdy každý proces z nějaké neprázdné množiny procesů je pozastaven a čeká na uvolnění nějakého zdroje s výlučným (omezeným) přístupem vlastněného nějakým procesem z dané množiny, který jediný může tento zdroj uvolnit, a to až po dokončení jeho použití.

**Blokování** (*blocking*) při přístupu do KS je situace, kdy proces, jenž žádá o vstup do kritické sekce, musí čekat, přestože je kritická sekce volná.

**Stárnutí** (*hladovění*, *starvation*) je situace, kdy proces čeká na podmínku, která nemusí nastat. V případě kritické sekce je touto podmínkou umožnění vstupu do kritické sekce.

### Atomické instrukce pro synchronizaci

Pro synchronizaci lze použít instrukce, jejichž **atomicita je zajištěna hardware**. *Používá se častěji* než specializované algoritmy bez využití atomických instrukcí.

Tato řešení zahrnují možnost **aktivního čekání**, proto se také často označují jako *spinlock*. Lze je užít na *krátkých*, *neblokujících* kritických sekcích **bez preempce**.

#### Instrukce test-and-set

Např. `LOCK BTS`.

```c
bool test_and_set(bool &target) {
	bool rv = target;
	target = true;
	return rv;
}

bool lock = false;  // shared variable

// ...
while (test_and_set(lock));
// critical section
lock = false;
// ...
```

#### Instrukce swap

Např. `LOCK XCHG`.

```c
void swap(bool &a, bool &b) {
	bool temp = a;
	a = b;
	b = temp;
}

bool lock = false;  // shared variable

// ...
bool key = true;    // local variable
while (key)
	swap(lock, key);
// critical section
lock = false;
// ...
```

### Semafory

**Semafor** (*semaphore*) je synchronizační nástroj nevyžadující (nebo minimalizující) aktivní čekání – aktivní čekání se v omezené míře může vyskytnout uvnitř implementace operací nad semaforem, ale ne v kódu, který tyto operace používá.

Jedná se v principu o *celočíselnou proměnnou* přístupnou dvěma základními **atomickými operacemi**:

- **lock** (také P či down) – *zamknutí/obsazení* semaforu, volající proces čeká, dokud není možné operaci úspěšně dokončit a
- **unlock** (také V či up) – *odemknutí/uvolnění* semaforu.

**Sémantika celočíselné proměnné** $S$ odpovídající semaforu:

- $S > 0$ – **odemknuto**,
- $S \leq 0$ – **uzamknuto**.

Hodnota $S > 1$ se užívá u zobecněných semaforů, jež mohou propustit do kritické sekce *více než jeden proces*.

Je-li $S < 0$, hodnota $|S|$ udává *počet procesů čekajících na semaforu*. Někdy se záporné hodnoty neužívají a semafor se zastaví na nule.

```c
semaphore mutex;  // shared semaphore

init(mutex, 1);
// ...
lock(mutex);
// critical section
unlock(mutex);
// ...
```

### Monitory

**Monitor** je jeden z vysokoúrovňových synchronizačních prostředků. Zapouzdřuje data, má definované operace, *jen jeden proces* může provádět nějakou operaci nad chráněnými daty. Pro možnost čekání uvnitř monitoru jsou k dispozici tzv. **podmínky** (*conditions*), nad kterými je možné provádět operace:

- `wait()` a
- `signal()`, resp. `notify()` – pokračuje příjemce (odesílatel má následně prioritu pro návrat), resp. odesílatel signálu.

## Běžné synchronizační problémy

### Problém producenta a konzumenta

Komunikace **producenta a konzumenta** přes vyrovnávací paměť s kapacitou omezenou na $N$ položek.

Synchronizační prostředky:

```c
semaphore full, empty, mutex;

init(full, 0);
init(empty, N);
init(mutex, 1);
```

Producent:

```c
do {
	// ...
	// produce an item I
	// ...
	lock(empty);
	lock(mutex);
	// ...
	// add I to buffer
	// ...
	unlock(mutex);
	unlock(full); 
} while (1);
```

Konzument:

```c
do {
	lock(full);
	lock(mutex);
	// ...
	// remove I from buffer
	// ...
	unlock(mutex);
	unlock(empty);
	// ...
	// consume I
	// ...
} while (1);
```

### Problém čtenářů a písařů

Libovolný počet čtenářů může číst; pokud ale někdo píše, nikdo další nesmí psát ani číst.

Synchronizační prostředky:

```c
int readcount;
semaphore mutex, wrt;

readcount = 0;
init(mutex, 1);
init(wrt, 1);
```

Písař:

```c
do {
	// ...
	lock(wrt)
	// ...
	// writing is performed
	// ...
	unlock(wrt);
	// ...
} while (1);
```

Čtenář:

```c
do {
	lock(mutex);
	readcount++;
	if (readcount == 1)
		lock(wrt);
	unlock(mutex);
	// ...
	// reading is performed
	// ...
	lock(mutex);
	readcount--;
	if (readcount == 0)
		unlock(wrt);
	unlock(mutex);
	// ...
} while (1);
```
